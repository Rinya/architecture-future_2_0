# Обоснование конфигурации Terraform для облачной инфраструктуры

Данный документ объясняет выбор ресурсов, их параметров и общие решения, принятые в проекте Terraform для среды Yandex Cloud. Он охватывает:

1. **Выбор ресурсов** – почему использован каждый тип ресурса.  
2. **Выбор параметров** – размер виртуальных машин, дисков, настройки NAT и т.д.  
3. **Декларативный подход** – преимущества написания инфраструктуры как кода в декларативном стиле.  
4. **Преимущества IaC** – воспроизводимость, масштабируемость и операционная эффективность.

---

## 1. Выбор ресурсов

| Ресурс | Назначение | Ключевые атрибуты |
|--------|------------|------------------|
| `yandex_vpc_network` | Создаёт изолированную частную сеть для всех ресурсов. | `name`, `description` |
| `yandex_vpc_subnet` | Логическое разделение VPC на подсети для веб- и БД-уровней. | `zone`, `v4_cidr_blocks` |
| `yandex_vpc_security_group` | Управляет входящим и исходящим трафиком. | `ingress` (SSH, HTTP, HTTPS), `egress` (весь) |
| `yandex_iam_service_account` | Учетная запись службы, которую Terraform использует для управления ресурсами. | `name`, `description` |
| `yandex_resourcemanager_folder_iam_member` | Предоставляет IAM‑роли для учётной записи службы. | `role` (editor, storage.admin) |
| `yandex_iam_service_account_static_access_key` | Генерирует статические ключи для доступа к Object Storage. | `description` |
| `yandex_mdb_postgresql_cluster` | Управляемый кластер PostgreSQL для хранения данных. | `environment`, `network_id`, `config` (версия, ресурсы) |
| `yandex_storage_bucket` | Bucket Object Storage для файлов состояния и артефактов. | `bucket`, `access_key`, `secret_key` |
| `random_id` | Добавляет уникальный суффикс к имени бакета, чтобы избежать конфликтов. | `byte_length` |
| `tls_private_key` | Генерирует пару ключей RSA для SSH‑доступа. | `algorithm`, `rsa_bits` |
| `local_file` | Сохраняет сгенерированный приватный ключ локально. | `content`, `filename`, `file_permission` |
| `yandex_compute_instance` | Виртуальные машины для веб‑сервисов и других задач. | `resources` (ядра, память), `boot_disk`, `network_interface`, `metadata` (SSH‑ключи) |
| `null_resource.error_handler` | Опциональный механизм очистки при ошибках. | `triggers`, `provisioner` (снимок состояния) |

## 2. Выбор параметров

### 2.1 Размер виртуальных машин

- **Ядра и память**: каждая VM создаётся с **2 ядрами** и **2 ГБ памяти** (`cores = 2`, `memory = 2`). Эта конфигурация является сбалансированным стартовым пунктом для лёгких веб‑сервисов или небольших нагрузок, обеспечивая:
  - Достаточный CPU для одновременных запросов.
  - Низкое потребление памяти, чтобы затраты оставались минимальными.
  - Возможность масштабирования горизонтально, добавляя новые инстансы, а не повышая размер одного VM.

- **Размер диска**: размер загрузочного диска установлен в **15 ГБ** (`disk_size = 15`). Такой размер покрывает:
  - Изображение Ubuntu 22.04 LTS (≈ 4 ГБ).
  - Место для системных пакетов, логов и данных приложения.
  - Буфер для будущих обновлений без необходимости немедленного изменения размера.

### 2.2 Настройка NAT

- `nat = true` в блоке `network_interface` включает выход в интернет для VM, оставляя её приватной. Это необходимо для:
  - Автоматических обновлений ОС.
  - Загрузки контейнерных образов или внешних зависимостей.
  - Поддержки безопасности за счёт отсутствия прямого доступа к внутреннему IP.

### 2.3 CIDR подсетей и зоны

- **Web‑подсеть** (`192.168.10.0/24`) и **DB‑подсеть** (`192.168.20.0/24`, `192.168.21.0/24`) размещены в разных зонах (`ru-central1-a`, `ru-central1-b`). Это обеспечивает:
  - **Высокую доступность**: БД‑кластер охватывает две зоны.
  - **Изоляцию сети**: отдельные CIDR‑блоки предотвращают случайный кросс‑трафик.
  - **Толерантность к отказам**: если одна зона испытывает сбой, другая остаётся доступной.

### 2.4 Правила группы безопасности

- **SSH (порт 22)**: открыто для `0.0.0.0/0` для административного доступа. В продакшене это ограничится известными IP‑адресами.
- **HTTP (порт 80)** и **HTTPS (порт 443)**: открыты для всего мира, чтобы обслуживать веб‑трафик.
- **Egress**: разрешён весь исходящий трафик (`protocol = ANY`) для поддержки внешних коммуникаций.

### 2.5 Управляемый кластер PostgreSQL

- **Версия 15**: последняя стабильная версия с улучшениями производительности.
- **Ресурсы**: пресет `s2.micro`, тип диска `network-ssd`, размер 10 ГБ – подходит для разработки или низкой нагрузки в продакшене.
- **Высокая доступность**: два узла в разных зонах (`ru-central1-a`, `ru-central1-b`).

### 2.6 Bucket Object Storage

- **Имя бакета**: объединяется с случайным суффиксом (`random_id`) для избежания конфликтов имён в разных средах.
- **Ключи доступа**: генерируются через статические ключи учётной записи службы, гарантируя, что только Terraform может управлять бакетом.

## 3. Декларативный подход

Модель Terraform означает, что конфигурационный файл описывает *что* должно быть, а не *как* это сделать шаг за шагом. Преимущества:

- **Ясность**: файл `main.tf` является единственным источником правды, который разработчики и операторы могут прочитать и понять.
- **Идемпотентность**: многократный запуск `terraform apply` приводит к тому же состоянию, предотвращая дрейф.
- **Контроль версий**: изменения фиксируются в Git, что позволяет откатывать, проводить ревью и вести аудит.
- **Модульность**: ресурсы группируются логически (сеть, безопасность, вычисления, хранение), упрощая переиспользование и замену компонентов.

## 4. Преимущества IaC: воспроизводимость и масштабируемость

### 4.1 Воспроизводимость

- **Согласованные окружения**: один и тот же Terraform‑код создаст идентичную инфраструктуру в любой учётной записи Yandex Cloud, обеспечивая синхронизацию staging, тестирования и продакшена.
- **Автоматизированные резервные копии**: `null_resource.error_handler` сохраняет состояние Terraform перед ошибками, облегчая восстановление.
- **Документация**: конфигурация одновременно является документацией; любой может просмотреть файлы `.tf` и понять архитектуру.

### 4.2 Масштабируемость

- **Горизонтальное масштабирование**: добавление новых VM‑инстансов сводится к расширению карты `var.vm_instances`; Terraform автоматически создаст новые ресурсы.
- **Масштабирование инфраструктуры**: кластер PostgreSQL можно масштабировать, изменив блок `config` (например, увеличить дисковый размер, добавить ресурсы) без ручных вмешательств.
- **Пайплайны IaC**: интеграция с CI/CD инструментами (GitHub Actions, GitLab CI) позволяет автоматизировать развертывание, тестирование и продвижение изменений инфраструктуры.

### 4.3 Операционная эффективность

- **Автоматизация**: ручные действия в консоли не требуются; все ресурсы создаются, обновляются и уничтожаются через скрипты.
- **Безопасность**: IAM‑роли ограничены (`editor`, `storage.admin`), а SSH‑ключи генерируются программно.
- **Наблюдаемость**: выводы (outputs) предоставляют IP‑адреса и идентификаторы сети, которые можно подключить к системам мониторинга и логирования.

## 5. Итоги

Конфигурация Terraform для Yandex Cloud была спроектирована с учётом:

1. **Обеспечения безопасной, изолированной сети** с чёткой сегментацией веб- и БД‑уровней.  
2. **Развертывания лёгких, экономичных VM**, которые можно масштабировать горизонтально.  
3. **Включения контролируемого выхода в интернет** через NAT при сохранении правил безопасности.  
4. **Использования управляемых сервисов** (PostgreSQL, Object Storage) для надёжности и снижения эксплуатационных издержек.  
5. **Принятия декларативного, IaC‑подхода**, который гарантирует воспроизводимость, контроль версий и простоту поддержки.

Следуя этим принципам, инфраструктура может развиваться вместе с потребностями организации, оставаясь стабильной, безопасной и экономически эффективной.
